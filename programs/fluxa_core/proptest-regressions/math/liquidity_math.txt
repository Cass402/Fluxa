### Documented Precision Limitations

#### Q64x64 Fixed-Point Arithmetic Characteristics
1. **Fractional Bits**: 64 bits for fractional part provides ~10^-19 relative precision
2. **Division Rounding**: Integer division truncates, causing systematic underestimation
3. **Multiplication Overflow**: Large intermediate values may exceed u128 capacity

#### Observed Precision Loss Patterns

**Single Conversion (liquidity ↔ amount)**:
- Typical loss: < 0.1% for moderate values
- Worst case: up to 10% for extreme price ratios or very small amounts
- Primary cause: Integer division truncation in Q64x64 operations

**Double Conversion (liquidity → amounts → liquidity)**:
- Typical loss: < 1% for moderate scenarios  
- Worst case: up to 20% for narrow tick ranges or small liquidity
- Amplification effect: Errors compound through multiple divisions

**Edge Cases with High Error**:
- Tick width < 500: Very narrow price ranges amplify rounding
- Liquidity < 1000 (token units): Rounding dominates signal
- Extreme tick positions (|tick| > 400,000): Large price ratios stress precision

#### Mathematical Invariants Maintained

Despite precision loss, the following invariants hold:

1. **Monotonicity**: Larger inputs always produce larger outputs (within precision limits)
2. **Bounds**: All results respect MAX_TOKEN_AMOUNT (18,446,744,073,709,551,615)
3. **Determinism**: Identical inputs always produce identical outputs
4. **No Overflow**: Checked arithmetic prevents silent wraparound
5. **Range Correctness**: Amounts correctly zero outside active price range

### Recommendations for Protocol Usage

1. **Minimum Liquidity**: Set protocol minimum to avoid rounding-dominated regions (suggest ≥ 10,000 tokens)
